まず、ちょっとした歴史について。 shadcn/ui が 2023 年 1 月にリリースされたとき、それは Radix 上に構築されました。当時、他にこれに近いものはありませんでした。スタイルのないヘッドレス コンポーネント、優れた API、優れたアクセシビリティは、何百万ものアプリで実証済みです。

数年経つと、Radix を構築したのと同じ人たちが新しいもの、[Base UI](https://www.base-ui.com) を構築しています。彼らは一度それをやったことがある。今、彼らは最初に学んだすべてを使って再びそれを行うことができます。

昨年、Base UI がベータ版にタグ付けされましたが、多くの人から Radix をそれに置き換えるつもりかどうか尋ねられました。私は、「本番アプリで行うべき最悪のことは、コンポーネント ライブラリを切り替えることです」と言いました。私はそう思っていました、そしてそれは今でも当てはまります。そこで、切り替える代わりに、shadcn のことを行いました。つまり、Base UI のすべてのコンポーネントを再構築し、同じ抽象化を維持し、ユーザーが選択できるようにしました。 12 月には、両方のライブラリに `npx shadcn create` が導入されました。 1 月には完全な Base UI ドキュメントが公開されました。

それから私たちはあなたがそれを使って何をしたかを見ました。

---

## なぜ今なのか

- **ベース UI は安定しています。** 1.6.0 で、毎週 600 万以上のダウンロードがあります。
- **改善され続けています。** チームは、新しくて便利なコンポーネントを定期的に出荷しています。
- **私たちはそれを使用しています。** 私たちが開始したすべての新しいプロジェクトは Base UI 上で実行されます。
- **これを使用します。** shadcn/create で作成されたプロジェクトは、基数 2 対 1 ではなくベース UI を選択するようになりました。

コミュニティはすでに呼びかけを行っています。正式に発表させていただいております。

---

## 何が変わったのか

- **新しいプロジェクトのデフォルトは Base UI です。** `npx shadcn init` を実行すると、Base UI がデフォルトで選択されます。
- **shadcn/create は最初にベース UI を表示します。**
- **ドキュメントのデフォルトは Base UI です。** コンポーネント ページは [Base UI] タブで開きます。 Radix ドキュメントはワンクリックでアクセスできます。

## これはあなたにとって何を意味しますか

**基数は非推奨ではありません。** 当社は引き続き基数をサポートしており、すべての更新と新しいコンポーネントは両方のライブラリに出荷されます (コンポーネントがベース UI にのみ存在する場合を除く)。

**移行する必要はありません。** Radix は成熟したテスト済みのライブラリです。現在も本番環境で実行しており、移行は行っていません。アプリが機能する場合は、出荷を続けてください。

**新しいプロジェクトには Radix をお勧めしますか?** フラグ 1 つで完了します:

```bash
npx shadcn init -b radix
```

`shadcn init` を非対話的に実行し、Radix を期待するスクリプトまたは CI がある場合は、`-b radix` を追加して同じパス上に維持します。

**レジストリを構築しますか?** 特定のライブラリを固定したい場合は、`registry:base` 構成を送信してください。何もないアイテムはベース UI として初期化されるようになりました。

**何か新しいことを始めませんか?** Base UI をお勧めします。

## 移行の準備ができたら

移行する必要はありません。ただし、必要に応じて、そのためのスキルを構築しました。

```bash
npx skills add shadcn/ui
```

次に、コーディング エージェントに次のように尋ねます。

```txt
migrate accordion to base-ui
```

デフォルトでは段階的です。プロジェクトがグリーンで出荷可能な状態を維持している間に、一度に 1 つのコンポーネントとその使用法を移行します。作業中は両方のライブラリが共存します。途中で停止して出荷し、来週戻ってくると、中断したところから再開されます。または、プロジェクト全体を一度に依頼してください。

### なぜコードモッドではなくスキルなのか?

コードを所有しているのはあなただからです。バリアントを追加し、クラスを変更し、新しいプロパティをスレッド化しました。 codemod は、あなたが触れたことのないコンポーネントを処理し、あなたが触れたコンポーネントを破壊します。

そこで私たちは代わりに知識を出荷しました。すべての名前変更、すべてのプロパティの変更、すべての動作の違いを両方のライブラリに対して手作業でチェックしました。エージェントはそれを読み、あなたが何を変更したかを把握し、それらの変更を引き継ぎます。

機械的なものはどこでも修正されます (`asChild` は `render` になりました)。動作の変更にはフラグが付けられ、サイレントにパッチが適用されることはありません。あなたが決めてください。

### 移行によって生じるもの

実行ごとに次の 3 つのことが残ります。

- **動作するコード。** 成功を報告する前に型チェックおよびビルドが行われます。
- プロジェクト ルートの `.migration/` 内の **コンポーネントごとのレポート**: 何が変更され、何が放置され、手動で検証する必要があるかについての短いチェックリストが含まれます。
- **git 履歴をクリーンアップします。** ブランチ上のコンポーネントごとに 1 つのコミット。ロールバックとはブランチを削除することです。

レポートは次のようになります。

```md title=".migration/accordion.md"
# accordion

<!-- date, strategy used, and the one-line verdict -->

## Changed

<!-- every file touched, with what changed and why -->

## Left alone

<!-- files that look related but were intentionally not touched -->

## Behavior changes

<!-- differences that compile fine but act differently. flagged, not patched -->

## Verify by hand

<!-- a short checklist: open, click, tab through. takes a minute -->
```

隠れた状態はありません。進行状況はファイルと git 履歴に保存されるため、どのエージェント、どのセッション、どの日でも、最後に停止したところから再開されます。

これは、Claude Code、Cursor、またはスキルをサポートする任意のエージェントで動作します。実際のプロジェクトでテストしました: 60 個以上のコンポーネント、そのうち 36 個は Radix 上にありました。完全な移行は、コンポーネントあたり約 10,000 トークンで約 25 分で実行されました。クリーンなビルド、カスタマイズはそのまま。
